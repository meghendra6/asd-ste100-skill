# 한국어 리라이트 규칙

한국어 대상 텍스트에 적용하는 규칙표다. 프로세스, 두 모드, 출력 형식, 프로젝트 글로서리 메커니즘, 구조/어휘 구분은 `SKILL.md`를 따른다. 이 파일은 무엇을 위반으로 잡을지를 정한다.

## 근거와 한계

ASD-STE100은 영어 전용 표준이고, 공인된 한국어 통제 언어 표준은 없다. 이 파일은 STE의 구조 원칙(한 문장 한 의미, 행위자 명시, 짧은 문장, 요점 선행)을 한국어 문법으로 옮긴 이 스킬의 자체 규칙셋이다. 공공기관의 쉬운 한국어 지침과 방향이 일부 겹치지만 그 지침을 따르지 않는다. 그 지침은 전문 용어를 한국어로 옮겨 쓰기를 권장하는데, 기술 문서에서 억지 번역은 원어 자료와의 대조를 끊어 중의성을 늘리기 때문이다(어휘 규칙 참고).

한국어에는 영어에 없는 중의성 원인이 있다. 주어와 목적어의 생략이 문법적으로 자연스럽고, 연결어미가 문장을 끝없이 이을 수 있고, 피동과 이중피동이 행위자를 지운다. 그래서 아래 표에는 영어판(`rules-en.md`)에 없는 규칙이 있다.

## 구조 규칙 — 확신하고 적용한다

| 규칙 | 하라 | 하지 마라 |
|---|---|---|
| 결론 선행 | "작업을 중지하십시오. 큐가 가득 찼고, 가득 찬 큐는 새 작업을 버립니다." — 결과·명령·경고가 문단을 연다 | 배경을 쌓다가 마지막 문장에서 요점을 내놓는 문단 |
| 주어·목적어 명시 | "에이전트가 파일을 삭제했습니다." | "삭제했습니다." — 한국어는 생략이 자연스러워서 이것이 가장 큰 중의성 원인이다. 기계 독자는 생략된 논항을 복원하지 못한다 |
| 한 문장 한 지시 | "파일을 여십시오. 3행을 읽으십시오." | "파일을 열고 3행을 읽은 뒤 일치하는지 확인하는데, …" |
| 연결어미 분리 | 문장을 끊는다 | "-고", "-며", "-는데", "-어서"로 지시나 주장을 잇기 — 연결어미는 문장을 끝없이 늘인다 |
| 문장 길이 | 지시문 ≤12어절, 설명문 ≤20어절 (STE의 20/25단어에 대응하는 이 스킬의 자체 기준) | 기준을 넘는 복합문 |
| 피동 제한 | 행위 주체가 있으면 능동: "스케줄러가 작업을 취소했습니다." | "작업이 취소되었습니다." — 누가 취소했는가? 행위자를 정말 모를 때만 피동을 쓴다 |
| 이중피동 금지 | "해결됩니다", "~로 보입니다" | "해결되어집니다", "~로 보여집니다" — 전면 금지 |
| 압축 명사구 해체 | 명사 나열은 3어절까지. 그보다 길면 주어와 동사가 있는 문장으로 푼다 | "구버전 scheduler의 Eagle cache-drop 오적용과 bonus slot 누락" 같은 개념 적층 |
| 지시어 금지 | 대상을 이름으로 부른다: "재시도 로직이" | "이것이", "그 부분이", "해당 이슈가" |
| 완전한 문장 | 주어·동사·조사를 갖춘 문장 | 화살표 나열(A → B → 실패), 조각문, 조사 생략("서버 재시작 후 확인") |
| 헤지 보존 | "실패했을 수 있습니다"는 그대로 둔다 | "실패했습니다"로 승격 — 추측을 사실로 바꾸면 다른 주장이 된다 |
| "-겠-" 제한 | 추측은 "~로 추정합니다", 예정은 "~할 예정입니다" | 추측·의지·미래가 겹치는 "-겠-" ("곧 완료되겠습니다") |
| 종결어미 통일 | 한 문서에 한 문체 (합쇼체면 끝까지 합쇼체) | 합쇼체·해요체·해라체 혼용 |
| 이중부정 금지 | "가능합니다" | "불가능하지 않습니다", "없지 않습니다" |
| 목록 사용 | 3개 이상의 단계나 조건은 번호·글머리 목록으로 | 순서를 산문 한 문장에 파묻기 |

## 어휘 규칙 — 방향으로만 적용한다 (글로서리가 있으면 강제)

| 규칙 | 하라 | 하지 마라 | 왜 여기서는 약한가 |
|---|---|---|---|
| 한 대상 한 이름 | 한 동작에 한 동사를 정해 매번 쓴다 (항상 "확인") | 같은 동작을 "확인"/"체크"/"검증"으로 돌려 부르기 — 한자어·외래어·고유어를 섞으면 독자는 셋이 다른 동작인지 알 수 없다 | 문서 안의 일관성은 검사할 수 있다. 어느 단어가 표준어인지 정하는 공인 목록은 없다. |
| 기술 용어는 영어 그대로 | scheduler, prefill처럼 통용되는 용어는 영어로 유지한다. 통용어가 아니면 첫 등장에서 한 줄로 정의한다 | 억지 번역("일정 처리기") — 원어 문서·코드와의 대조가 끊겨 중의성이 늘어난다 | 어떤 용어가 "통용"인지는 분야에 따라 다르다. 프로젝트 글로서리가 있으면 그 표를 따른다. |
| 명사화 해소 | "분석하십시오", "검토합니다" | "분석을 수행하십시오", "검토를 진행합니다", "점검을 실시합니다" — 동작을 명사에 얼리고 뜻 없는 동사를 붙인다 | 동사형 선호는 어디서나 안전하다. 이것은 방향이 아니라 사실상 구조 규칙에 가깝다. |
| 번역투 제거 | 아래 대응표의 오른쪽 | 아래 대응표의 왼쪽 | 대응표는 대표 사례다. 전체 목록이 아니므로 같은 냄새가 나면 같은 방식으로 고친다. |

### 번역투 대응표

| 쓰지 마라 | 써라 |
|---|---|
| ~하는 것을 가능하게 합니다 | ~할 수 있습니다 |
| 성공적으로 완료되었습니다 | 끝났습니다 |
| ~로 인하여 / ~로 인해 | ~ 때문에 |
| ~에 있어서 | ~에서, ~에게 |
| ~를 통해 (수단이 아닐 때) | ~로 |
| ~에 대하여 / ~에 대한 (남용) | 조사로 직접 연결 ("서버에 대한 설정" → "서버 설정") |
| 주목할 점은 ~라는 것입니다 | ~입니다 |
| ~가 요구됩니다 | ~해야 합니다 |

## 스캔 체크리스트

영어판과 같은 9항목이다. 7개는 기계적이라 위반한 단어나 위치를 짚을 수 있고, 8번과 9번은 판단이 한 번 필요하다. 리라이트 전에 9개 전부를 훑는다.

1. **동의어 회전** — 같은 대상이 "확인/체크/검증"처럼 돌아가며 불린다. 고치기: 하나로 통일한다.
2. **헤지 스태킹** — "~일 수도 있지 않을까 생각됩니다"처럼 한정 표현이 쌓여 아무것도 주장하지 않는다. 고치기: 쌓인 헤지를 하나로 줄이되, 원문의 확신 강도는 유지한다. 헤지를 지우는 것과 헤지 더미를 정리하는 것은 다르다.
3. **명사화** — "분석을 수행하다", "검토를 진행하다". 고치기: 동사로 쓴다 ("분석하다").
4. **마케팅 형용사와 태도 표지** — 품질을 보여주는 대신 주장하는 말: "완벽한", "강력한", "매끄러운". 진정성을 주장하는 말도 같다: "솔직히", "사실", "분명한 것은". 고치기: 지우거나, 주장을 뒷받침하는 수치로 바꾼다.
5. **문장 잇기** — 연결어미와 쉼표로 여러 주장이 한 문장에 묶인다. 고치기: 한 문장 한 주장.
6. **번역투** — 위 대응표의 왼쪽 표현. 고치기: 오른쪽으로 바꾼다.
7. **묻힌 결론** — 문단의 주장·명령·경고가 빌드업 뒤 마지막 문장에 온다. 고치기: 첫 문장으로 옮긴다.
8. **"~가 아니라 ~이다" 구문** — 기각할 주장에 문장 절반을 쓴다 ("캐시 문제가 아니라 경쟁 조건입니다"). 고치기: 참인 쪽만 서술한다 ("경쟁 조건입니다"). 오해가 실재하고 이름 붙일 가치가 있을 때만 대비를 유지한다.
9. **신조어** — 정의 없이 만든 라벨을 기정 용어처럼 재사용한다. 고치기: 평문 서술로 바꾸거나, 첫 등장에서 한 번 정의하고 그대로 재사용한다.

## 출력 라벨

한국어 출력에서는 `Kept as-is:` 대신 `유지:`를, `Ambiguous:` 대신 `중의성:`을 쓴다. 의미와 사용 조건은 `SKILL.md`의 Output Format과 같다. 한 줄씩만, 보고할 것이 없으면 생략한다.
